# P1 试点裁决：table 法重解析 ds3 xls —— **否决，维持 naive**

- 日期：2026-09-02；试点对象：洪水统计(1).xls、水位库容曲线推求.xls（audit F1 病灶最重的两份）
- 结论先行：RAGFlow v0.27.1 的 `table` chunk_method **治不了**政府 BIFF 表的合并表头/标题行错位，
  在最重的曲线表上产出 **2.5× 块数 + 94% 垃圾 + "值当表头"**，属净倒退。两文档已回滚 naive。

## 二、试点换来的 v0.27.1 机制事实（比 A/B 本身更值钱）

1. **tag 阶段 = ES 打标失败后逐块调 LLM**（`content_tagging`，task_executor.py:576 起）。
   闸门读 **KB 级** `parser_config.tag_kb_ids`；doc 级置 `[]` **无效**（且空数组会被 deep-merge 丢弃）。
   xls 行块几乎全部落入 LLM 兜底 → 12 块的表打了 200+ 次调用。正确关法：KB 级临时置空，
   串行解析完后恢复（已存块的 TAG_FLD 不受影响）。实测关掉后：**34 秒/文档，0 次 LLM**。
2. **doc 级 `auto_questions=0` 有效**（task["parser_config"] 路径），是压 LLM 成本的合法手段；
   `tag_kb_ids` 恰恰相反（走 kb_parser_config 路径）。
3. **Excel 加载器三层降级**：openpyxl → pandas 默认引擎 → **calamine**（Rust 读引擎）。
   这批损坏 BIFF 只有 calamine 能读（openpyxl/xlrd/pandas 默认全部失败）。
4. **Redis 队列消息在容器重启后会被重新领走执行**（未 ack 消息重新投递）——重启前未跑完的 parse
   重启后会"复活"，与人工重发的任务**并发双跑**。表现为双任务接连完成 + document.chunk_num 虚增
   （ES 实际块数正确、无重复）。重启前应确认队列无在途任务。
5. 无 stop-parse 端点（DELETE parse → 405）；"取消"只有重启一招。
