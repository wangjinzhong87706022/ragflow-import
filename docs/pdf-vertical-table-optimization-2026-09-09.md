| 项 | 结论 |

## 1. 问题分析

### 1.1 源文件特征

对 128 页逐页做三层探测（`01_detect_table_pages.py`）：

1. **文字层探测**：`page.get_text()` 全部为空 —— 纯扫描件，无可提取文字；
2. **矢量图形探测**：`page.get_drawings()` 全部为空 —— 表格线不是矢量，无法用线条法定位表格；
3. **页面方向探测**：`page.rect` 全部为纵向（w < h），`page.rotation` 全为 0 —— 旋转发生在**图像内容内部**，PDF 结构层面不可见。

结论：只能**把每页渲染成图像做像素级分析**。

### 1.2 表格页识别（图像水平线检测）

对每页渲染 100 DPI 位图，逐行统计最长连续暗像素游程（>30% 页宽记为一条横向表格线）：

- `line_density > 0.03 且 fill_ratio > 0.02` 判为表格页；
- 命中 17 页：p70-80（11 页）、p83-84、p89、p91-92、p95。

### 1.3 视觉复核（区分两类表格）

渲染 150 DPI 缩略图人工确认，17 个命中页分两类：

| 类型 | PDF 页 | 内容 | 是否旋转 |
|---|---|---|---|
| 竖向窄表 | p70-80 | D.0.1-1/1-2/1-3 工程特性表（3-4 列，名称/单位/数量） | 否 |
| **横排大表** | **p83, p84, p89, p91, p92, p95** | **D.0.4 土地利用、D.0.5 水土流失、D.0.13 图斑设计、D.0.15 措施量汇总、D.0.16 工程量汇总、D.0.20 效益计算** | **是（顺时针 90°）** |

### 1.4 初始方案（旋转）与失败教训

第一版思路是物理旋转后导入（`02_rotate_pages_abandoned.py`）：

- **教训 1（页码判错）**：首次按"印刷页码"误转了 p76/p77（实为竖向的 D.0.1-2 续表），旋转渲染复核时才发现标题方向不对；改为按 PDF 绝对页码只转真正的 6 页。
- **教训 2（上传 413）**：13MB multipart 用 urllib 手拼 boundary 上传返回 `413 Request Entity Too Large`；改用 `requests` 库的标准 multipart 编码同文件成功 —— 手拼 multipart 的格式瑕疵会触发代理限制。
- **教训 3（解析不自动启动）**：API 上传后 `run=UNSTART`，必须显式调 `POST /datasets/{ds}/documents/parse`。
- **教训 4（旋转收益有限）**：旋转版导入的表格仍以结构欠佳的块输出，且旋转破坏原文档。

**用户决策：放弃旋转，直接使用 RAGFlow 原生能力，参照已成功解析的 `SL-T-447-2026_p79-96(2).pdf` 的配置。**

## 2. 优化方案（最终采用）

### 2.1 参照配置的 key 差异

对比 p79-96(2).pdf（旧摘录，解析质量最好的一版）与裸上传的 parser_config：

```jsonc
{
  "chunk_method": "naive",
  "parser_config": {
    "chunk_token_num": 512,
    "delimiter": "\\n!?;。；！？",
    "layout_recognize": "DeepDOC",
    "html4excel": false,
    "filename_embd_weight": 0.1,
    "ext": { "table_vision_enhance": true }   // ← 关键差异
  }
}
```

`table_vision_enhance=true` 让 VLM 在表格识别阶段对每个表格区域做视觉重建（含旋转内容），输出 Markdown 表格 —— 这正是"不旋转也能正确解析竖排表格"的机制。该字段不在本地 ragflow 仓库代码中（服务器版本较新），且 PATCH schema 只接受 `ext` 内的写法，服务端会同步回显到顶层。

### 2.2 关键 API 语义（本次实测确认）

| 操作 | 正确端点 | 备注 |
|---|---|---|
| 上传文档 | `POST /api/v1/datasets/{ds}/documents`（multipart，`requests` 实现） | 13MB 可过 |
| 更新解析配置 | `PATCH /api/v1/datasets/{ds}/documents/{doc_id}` | PUT/POST 均 405 |
| 写 vision enhance | `parser_config.ext.table_vision_enhance=true` | 顶层写法被 schema 拒绝（Extra inputs） |
| 触发解析 | `POST /api/v1/datasets/{ds}/documents/parse`，body `{"document_ids":[...]}` | 上传后必须显式触发 |
| 查 chunk | `GET /datasets/{ds}/documents/{doc}/chunks?page=&page_size=` | **page_size ≤ 100** |
| chunk 数量可信度 | 以 chunks 接口 `data.total` 为准 | 文档列表的 `chunk_num` 字段不可靠（曾显示 0） |
| 删除文档 | `DELETE /api/v1/datasets/{ds}/documents`，body `{"ids":[...]}` | 单文档 DELETE 405 |
| 删除 chunk | `DELETE /api/v1/datasets/{ds}/documents/{doc}/chunks`，body `{"chunk_ids":[...]}` | 单块 DELETE 405 |
| QA 问答 | `POST /api/v1/chats/{chat_id}/completions`，`stream:false` | response.data.answer / .reference.chunks |

### 2.3 执行流程

1. 删除旋转版测试文档（batch DELETE）；
2. 上传**原始未旋转** PDF，命名 `SL-T-447-2026.pdf`；
3. `PATCH` 写入 `ext.table_vision_enhance=true`（验证回显：顶层与 ext 均为 true）；
4. `POST /documents/parse` 触发解析，15s 间隔轮询，约 **30 分钟**完成；
5. 全量拉取 128 chunks，异常扫描后删除 1 个乱序碎片块（p85 `79658b21`，竖排表头残字 + 注记混排）→ **127 chunks**。

### 2.4 解析结果

- **35 个 Markdown 表格块**（HTML 表格 0 个）+ 92 文本块；
- 竖排大表全部重建为结构正确的 MD 表格，例如：
  - D.0.5 水土流失现状表（p84）：13 列，列头 分区/省/县/乡镇/小流域/总面积/水土流失总面积/轻度~剧烈占比/侵蚀模数/沟壑密度 全部正确；
  - D.0.6 崩岗现状表（p85）：15 列，崩岗类型/形态/沟道要素正确；
  - D.0.11 坡耕地坡度组成表（p88）：带题注，<5°~>25° 五级 × 面积/占比 结构正确。

## 4. 复现步骤


## 6. 经验沉淀

1. **扫描件竖排表格首选 `table_vision_enhance`，不要物理旋转**：VLM 在表格区域级做视觉重建，旋转反而破坏原文档且收益有限。
2. **评测必须逐块核对，不能凭旧版本经验下"缺表"结论**：本次两次"缺表"误判（D.0.2/D.0.19）均因多表合并块与嵌入题注未被表面扫描发现。
3. **多表合并块是双刃剑**：p82/p87/p94 单块含 2-3 张表，覆盖完整但题注可能错位（p82 案），评测时要看块尾而不只看块头。
4. **文档列表 `chunk_num` 不可信**；`/documents/parse` 必须显式触发；multipart 上传用 `requests`。
