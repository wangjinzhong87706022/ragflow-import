## 一、背景与决策链

全库审计（`out/doc_audit/AUDIT.md`）定级 F1：政府 BIFF 表经 RAGFlow naive 解析产生合并表头错位的
`Unnamed: N/nan` 行垃圾，数值与列名割裂（"无法判断 6879 是弃水量还是降雨量"），且同表 ~30 个
同头块在检索中互相分流。优化菜单 P1（table 法重解析）经试点后**否决**：

| 文档 | naive | table | 裁决 |
|---|---|---|---|
| 洪水统计(1).xls | 12 块 | 23 块 | 行键略改善，站列仍 Unnamed；目标块被挤出 top10 |
| 水位库容曲线推求.xls | 523 块 | **1331 块，94% 垃圾，值当表头** | 明确回归 |

试点同时换得 v0.27.1 机制实录 8 条（tag 阶段逐块 LLM 兜底只读 KB 级 `tag_kb_ids` 闸门、
Excel 加载三层降级 openpyxl→pandas→**calamine**、Redis 队列重启复活双跑、无 stop-parse 端点等，
详见 `PILOT_TABLE_VERDICT.md` §二）。两文档已精确回滚（12/523 块）。

**用户裁定**（2026-09-02）：xls 问题走**选项 B——定向融合文本**：挑 QA 高价值的少数 xls，
离线读数 → 人工校对表头 → 融合文本 → 复用 12 图管线经验导入。ds4 的 3 份 xlsx 与选项 C
（离线表头分类局部 table 化）不在本轮范围。

## 二、语料调查（27/27 份读通）

**读取通道**（关键约束）：本机与各 venv 均无 python_calamine，openpyxl/xlrd/pandas 默认引擎
对这批损坏 BIFF 全部失败；唯一通路是 RAGFlow 容器内置 calamine 的 **stdin 流式只读**：

```bash
cat <file.xls> | docker exec -i -e PYTHONIOENCODING=utf-8 docker-ragflow-cpu-1 \
  python3 -c '...pandas.read_excel(io.BytesIO(b), engine="calamine", header=None)...'
```

（容器名是 `docker-ragflow-cpu-1` 而非 `-server-1`；语料目录未挂载进容器；提取产物
`out/xls_fusion/survey/extract_<KB名>.json` 存原始网格供逐值复核。）

**选定 3 份**（按 QA 价值 × 垃圾收敛性价比）：

| KB 名 | 语料路径 | 现块数 | 内容 |
|---|---|---|---|
| 洪水统计(1).xls | 06-历年洪水资料/06-2008年洪水(8-22)/洪水统计.xls | 12 | 8.21 洪水全链条：13 站日降雨 + 岔口弃水 + 柳林来水 + 水库弃水（全库站网最宽） |
| 较大洪水统计表.xls | 06-历年洪水资料/08-历年洪水统计/较大洪水统计表.xls | 27 | 1867 年以来 49 场洪水目录（每行一个可问答事实，QA 密度最高） |
| 2011年下泄水量统计.xls | 06-历年洪水资料/08-历年洪水统计/2011年下泄水量统计.xls | 101 | 110905/110911/110918 三场 + 全年泄水与 4 次溢流（ds3 第二大垃圾生产者，101→约 30 块收敛） |

不碰 `水位库容曲线推求.xls`（ds2 图表壳已覆盖曲线主题，且是 table 试点失败案例）。

**融合文本必须处理的 6 类结构病灶**：左右双表同 sheet（8.21 降雨 sheet 列 0-14 雨量 / 15-21 岔口弃水；
较大洪水统计表 r21+ 右侧调蓄块）、上下双表同 sheet、日期纵向承袭（合并单元格需 forward-fill）、
裸 Excel 序列日期（43333=2018-08-21、40789=2011-09-03 等，origin 1899-12-30）、表头行位置不固定且
2 级合并、标题行是唯一事件标识且**标题本身有错**（见下节；另 2001年洪水过程线.xls 实为 2010.7.24、
05-2013 洪水过程.xls 入库 sheet 标题写 20110729）。另有浮点噪声（7.4879999999999995 类）需 round。

## 三、重大发现：目录「2008年洪水」实为 2018年8月21日洪水

`06-2008年洪水(8-22)/` 目录下 3 份 xls 在 KB 中的元数据为 `flood_event="2008-8", year=2008`，
但数据内部**一致指向 2018 年**，四条独立证据：

1. 来水 sheet 标题即「"20180821"洪水」；
2. Excel 日期序列 43333/43334/43335 = 2018-08-21/22/23（origin 1899-12-30 换算）；
3. **《较大洪水统计表》180821 行与本表逐值互证**：洪峰 466、最大一日 958 / 三日 1308 万m³、
   柳林断面实测 383 m³/s；
4. 洪水目录中 2007→2010 年间没有任何 2008 年场次（该时段最小场次洪峰仅 55 m³/s，2008 若有
   洪水不可能缺席）。

**波及面**：`METADATA_SCHEMA.flood_event` 枚举从目录名衍生（`FLOOD_EVENT_BY_SUBDIR`，
config.py:167），因此枚举缺 `2018-8`；同目录 3 份 xls（洪水统计/降雨量统计/弃水计算）元数据
全部归因错误，`sub_category="2008年洪水(8-22)"` 同病。

**处置**（本批约定不动 `src/`）：3 份融合文本按真值 2018 年撰写；壳文档元数据建议
`flood_event="其他", year=2018, sub_category="2018年洪水(8-21)"`；枚举扩 `2018-8` 与
`FLOOD_EVENT_BY_SUBDIR` 纠偏、同目录另 2 份未动桩文档的元数据纠偏，留待用户单独裁定后
作为独立小任务处理。

## 四、方案设计（xls 壳模式）

### 4.1 导入模式

壳与垃圾块**同一文档**（png 管线的"新壳 + 旧 md 是两个文档"不成立），故走：
**删旧 naive 文档 → 重传同名 xls 保持 UNSTART（不 parse）→ patch 11 字段元数据 → 手动挂融合切片
→ 探针验证 → 下一份（严格串行）**。机制依据（均已验证）：手动挂载切片无需 parse 即入检索索引；
壳保持 UNSTART 不产生解析分片，从而**自然绕开 tag 阶段逐块 LLM 兜底**（KB 级 `tag_kb_ids`
无需动）；`PUT status:"0"` 静默失效，下架只能删除。该模式完全避开未经测试的 chunk 级 DELETE 端点。

### 4.2 融合文本格式（沿用 12 图管线 5 段式）

头部 blockquote（来源+鉴定方法+事件定性）→ 行文本（**一行一事实、自包含**：事件前缀注入每行、
日期 ffill、序列日换算、双词形「毫米/mm」「立方米每秒/m³/s」「万立方米/万m³」）→
`## 关键数值速查（双词形）` → `## 常问速查`（每份 ≤8 条 问：…答：…，吸取 239 行 QA 轰炸教训）→
`## 仲裁留痕`（双表拆分、标题错误、口径区分、剔除项）。数值全部经交叉验证（如 2011 弃水 10561
与洪水目录逐值吻合；8.21 洪峰 466/383 与目录 180821 行互证）。

### 4.3 产物与脚本（全部在 `out/xls_fusion/`，src/ 零改动）

| 文件 | 作用 |
|---|---|
| `extract_xls.py` | 离线读数器（本机 calamine 优先、docker stdin 兜底），产 `survey/extract_*.json` |
| `fusion/*.md` ×3 | 融合文本（28 切片，143–503 字/片，锚点全覆盖自检通过） |
| `questions_xls.jsonl` | 12 题检索层题库（全部 coverage=fusion，锚点出自 3 份目标 xls） |
| `run_eval_xls.py` | before/after 评测（×3 取多数，DS_IDS=[ds3]） |
| `probe_xls.py` | 8.21 同头垃圾探针 + 逐文档锚点探针 |
| `rollout_xls_shell.py` | 壳迁移（存档→删→传壳→patch→挂片→探针门 FAIL 即停；`--apply`/`--only`/`--rollback`；`shell_state.json` 幂等、`manifest_xls_shell.json` 台账） |
| `xls_chunks_archive.json` | 删前全量块存档（含原 chunk_method/parser_config/meta 快照，回滚依据） |
| `REVIEW.md` | 人工评审门说明（含两个待裁定点） |
